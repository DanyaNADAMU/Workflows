# Модель доверия каталога workflows

## Ноль секретов — намеренно

Этот каталог публичен, потому что переиспользуемые workflows GitHub можно
подключать только из публичного репозитория (или из своего же). Раз «публичен»
означает «читаем всем миром», репозиторий спроектирован так, что его полная
утечка ничего не стоит:

- Ни токенов, ни приватных ключей, ни инвентаризации хостов здесь не
  появляется никогда.
- Каждый нужный workflow-у креденшел объявляется **по имени** в интерфейсе
  `workflow_call` и заводится в секретах **вызывающего** репозитория,
  попадая внутрь через `secrets: inherit`.

## Право на действие живёт там, где действие происходит

Каждый workflow построен вокруг принципа «ключ не путешествует дальше
машины, где он используется»:

- **Ключ зеркалирования (push)** — существует только в секретах вызывающего
  репозитория; его открытая половина на git-сервере закреплена за forced
  command (`git-receive-pack '/home/git/<Repo>.git'`), поэтому ключ не может
  ничего читать или попасть в шелл.
- **Деплой-ключ** — собственный ключ сервисного пользователя; его открытая
  половина на целевом хосте закреплена за `deploy-service <service> <digest>`,
  так что утечка ключа позволяет лишь перекатить один сервис на один digest
  образа.
- **Ключ GetBlock** — используется только шагом перекрёстной сверки
  `ots.yml`, внутри задачи вызывающего репозитория, и никогда не
  материализуется здесь.

## Шлюзы верификации

- Коммиты и теги подписаны SSH-ключом (`danya-git`); якорь доверия —
  `.allowed_signers`, история запечатана в биткоин через OpenTimestamps.
- Потребители закрепляются на `@v1` — подписанном аннотированном теге;
  переподписанный `v1` — единственный путь, которым изменение workflow
  доходит до потребителей.
- `git tag -v` обязателен на каждом зеркальном checkout перед деплоем:
  оператор проверяет цепочку подписей, прежде чем довериться релизу.
